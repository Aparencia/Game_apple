## 0. 结论速览

### 0.1 三个方向，按顺序

| 顺序 | 方向 | 解决什么 | 为什么排这里 |
|---:|---|---|---|
| 1 | **可重复**：基线持久化 + 正常上电不动阀 + session/20 Hz 原始流 + PC 回放 | 每次上电要擦干电极、要人工确认、日志无法复现 | 不做这个，后面任何改动都无法验证，也无法做 20 次统计 |
| 2 | **可辨识**：内杯 + 立管 + 独立“有水”信号；固定几何后收敛为单基线 | EC 同时被液位、阀位、流动状态（以及温度补偿残差）污染；三槽在补一个不该由软件补的问题 | 这是延迟、误判、标定复杂度的共同上游；结构改动周期最长，要尽早启动 |
| 3 | **安全与达标**：硬件 IWDT/保险丝（与第 1 项并行）、阀位反馈、流量计、速率抢先 | 软件看门狗盖不住关中断；无阀位/无流量，回收率与“卡阀”都不可观测 | 安全项可立即做；阀位/流量/速率等 P/H 稳定后再做，避免在移动靶上打补丁 |

### 0.2 不建议再做

- 不再用**单份现场日志**去调 `d1 / d2 / trim / SOAP_LATCH`；07:39 的日志证明失败点是状态耦合，不是阈值差几毫伏。
- 不在结构未改前承诺“≤1.5 s”；当前物理时间常数 τ 是 30~200 s 量级，算法的眼睛看的是几十秒前的水。
- 不把 HC-SR04 当唯一液位（现场日志 `valid=0`，泡沫/安装都会失效，`M2h_SOAP_LATCH_20261121.md` §10）；不买压力式液位（量程不匹配，v3 §6.1 已排除）。
- 不先上 ORP / 阻抗 C / UV；它们补的是 B 类盲区，不解决 P/H/Q 耦合。
- 不做大爆炸式重写；`app_main.c` 只做**按职责抽取**，每次抽取后必须能回放同一批日志。

### 1.3 07:39 现场日志说明了什么

M2j 的修复依据（`Docs/CHANGELOG.md` v2.8.0-LEVEL-M2j）：

1. 07:39:43 提示 `CAL RECOVER`；07:39:58（15 s）`recover_skipped`；
   `SLOTS DRAIN=280.5 RECOVER=INVALID FULL=INVALID`，OLED `Auto fail`。
2. 07:40:08 仍然 `STATE to=CLEAR` / `VALVE pos=RECOVER`，而 RECOVER 槽无效；
   `dEC=5.9 mV`、`ec0≈291`（DRAIN 槽 280.5），水还在上涨。

这不是“阈值偏了几毫伏”，而是一条**状态耦合链**：

```
充水 → trim 以 4 mV/s 把基线从 280.5 抬到 291
     → dEC 从 16.5 掉到 5.9
     → 分类器判 L0
     → 阀申请 RECOVER
     → 但 RECOVER 槽 INVALID，用的仍是 DRAIN 槽基线
     → 回收位 + 无效槽 + 被学掉的基线，三条同时成立
```

M2j 的处理（`trim` 默认关闭、RECOVER 槽无效时禁止自动回收、确认窗 15→60 s、切槽当 tick 重算）是**正确的止血**，但它们是在耦合链的每个出口加闸门，不是拆掉耦合。代价是可用性进一步下降：部分标定不再能回收，确认窗口更长，标定更像“服务流程”。

> 结论：继续沿这条线打补丁，收益会越来越低；必须换一层来解。

## 2. 根因模型：三个变量被绑在一起

### 2.1 现在的环

```
EC ──> P（有没有水/浸没） ──┐
 │                          ├──> PERMIT ──> 阀位
 └──> Q（水脏不脏） ─────────┘                 │
                                              ▼
阀位 ──> H（槽选择） ──> Q 的基线（EC0/NTU0）
                 ▲
                 └── 超声液位（现场常 valid=0，实际退化为只看阀位）
```

环在哪里：`Q` 的基线由 `H` 选槽决定，`H` 主要由阀位决定，而阀位又由 `PERMIT` 决定，`PERMIT` 又由 `Q` 决定。**基线可以随“阀刚刚切到哪里”改变，而阀的位置又由基线算出的结论决定。** 这就是 07:40 那条链的结构性原因。

### 2.2 目标：把 P、H 变成独立量

```
浮球/导通/光电 ──> P ──┐
固定几何（内杯+立管）──> H ──┼──> PERMIT
EC/NTU（对持久化基线）──> Q ──┘
```

三条要求：

1. **P 不由 EC 推**：独立二值信号；浮球闭合必须蕴含“电极浸没”（装在电极尖同高或高 2~3 mm）。
2. **H 由结构钉死**：立管定液位，阀在杯下游，开关阀不改变杯内液位；这样“阀位”不再是一个需要单独标定的水力平台。
3. **Q 只在稳定态更新**：充水/排水/换向窗口内冻结或作废基线；`trim` 在拿到独立 H 之前保持关闭（M2j 的默认值就是对的）。

> 如果这三条成立，三槽、`trim`、SOAP_LATCH 的时间策略都可以大幅简化；如果结构不改，只能在现有环里继续加闸门。

## 3. 必须先做的三个决策

### D1　三槽自动标定：保留、收缩，还是取消？

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A 保留三槽 + 人工确认（M2j 现状） | 每次上电/每次标定走 DRAIN→RECOVER→FULL，人工确认 | 不改结构，安全侧有闸门 | 每次上电要擦干+确认；FULL 语义混；可用性最差 | **只作为过渡** |
| B 持久化三槽 + 仅服务模式标定 | 正常上电只加载基线、不动阀；三槽标定需显式服务模式 + 回收支路物理断开 | 消除每次上电标定；保留现有算法 | 仍需三槽；换水/换结构要重标 | **赛后 1~2 周做这个** |
| C 固定几何 + 单基线 + P 门控 | 内杯+立管固定液位；一个基线；标定在 DRAIN 位完成（回收支路隔离） | 最简单、最可辨识；三槽/trim 可删 | 需要结构改动与重新验证 | **结构改造后的终态** |

**建议**：B 作为过渡（先解决“每次上电”的问题），C 作为终态（结构固定后收敛）。不要在 A 上继续加复杂度。

### D2　“有水”信号选什么？

| 方案 | 成本 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 浮球开关（常开） | 5~10 元 | 二值、抗泡沫、与水质无关 | 有运动件，可能卡 | **首选** |
| 不锈钢导通针 | 2 元 | 最快、最便宜 | 结垢/电解、需交流激励 | 台架可用，长期不推荐 |
| HC-SR04 | 已有 | 连续液位、可做趋势 | 泡沫/安装/温补都未解决，现场 `valid=0` | **降级为诊断**，不作唯一 gate |
| 流量计（主路） | 15~30 元 | 在流 + 累计水量 | 需按实际流量选型；不能用 30~120 mL/min 那款 | **第二阶段加**，用于水量与零流联锁 |

### D3　结构改不改？——用三个实验决定，不靠争论

| 实验 | 做法 | 通过判据 | 不通过的含义 |
|---|---|---|---|
| **E1 阀位-液位解耦** | 内杯+立管固定液位，在**相同流量、相同液位**下，同一杯水分别在 DRAIN/RECOVER 阀位测 EC，重复 10 次 | 两阀位 EC 差 ≤5 mV，重复性 ≤2% | 阀位/流路耦合仍在，单基线不成立，需先做电气/流路处理 |
| **E2 阶跃响应** | 清水→皂液→清水，2~8 L/min（记录实际 Q），20 次；记录 τ、首次动作延迟 | 在 ≥2 L/min 下 τ ≤1.3 s；脏水路径 P95 ≤1.5 s（目标 ≤1.0 s） | 结构收益不足，需改流量/内杯尺寸或接受延迟上限 |
| **E3 低水位/湿膜** | 空腔、8~10 mL 低水位、湿膜、正常浸没各 20 次 | 低水位/湿膜 0 次判“有水”；正常浸没 0 次判“无水” | 浮球位置/阈值不对，先修 P 再谈 Q |

> E1 是“单基线是否可行”的判据；E2 是“结构改造是否值得”的判据；E3 是“P 是否真的独立”的判据。三个实验都不贵，但能把路线从“猜”变成“选”。

## 5. 指标：从“一次演示”变成“分布”

| 指标 | 现状 | 目标 | 测法 |
|---|---|---|---|
| 湿腔上电可用 | 需排空/擦干 + 人工确认 | ≤5 s 自动可用，0 人工 | 断电 20 次，记录到 `MEASURE` 的时间 |
| 标定 | 每次上电 20~30 s + 确认 | 仅服务模式，≤60 s | 标定日志 + 计时 |
| 误回收（皂液进回收桶） | 单次演示 0，无统计 | 80 次（20×4）0 次；只给 95% 上限（约 3.7%），不写“≤1%” | 20 次×4 场景 + 目视/电导复核；要把上限压到 1%，需约 300 次 0 事件 |
| 脏水动作延迟 | 设计口径 ~1.6 s；审查口径典型 2.2~5.7 s、最坏 7.7 s | P95 ≤1.5 s（目标 ≤1.0 s） | `# EVENT`/`# VALVE` 时间戳 |
| 清水确认 | ≥1.2 s（连续 3 块） | P95 ≤2.0 s | 同上 |
| 首段水损失 | 150~760 mL（最坏 ~1 L） | ≤100 mL | 称重/量杯 |
| 低水位误判 | 8~10 mL 不回收（目标） | 20/20 不回收 | E3 |
| 回收量/回收率 | 未测 | 可对账（流量计或称重） | 累计水量 vs 回收桶增重 |
| 无故障运行 | 未测 | 72 h：0 复位、0 卡阀、0 丢 session | 长稳日志 |
| 回归覆盖 | 0 | 12 场景 + 20 Hz 回放 | CI/本地脚本 |

> 安全指标的表述纪律不变：**不写“准确率”**，只写“误回收次数/上限、延迟分布、水量”；不把相对浊度写成 NTU；不写“达到 GB/T 18920”。

## 6. 为什么不先做“更聪明的判据”

1. **信号不可辨识**：同一杯水在三个平台下的 EC 差 28~47 mV，与真实皂液增量（+33~42 mV）同量级（设计文档 §6.4）。在这个信噪比下加特征，只是把拟合目标换成另一份日志。
2. **延迟的地板是 τ**：25 mL @ 3 L/min ≈0.5 s；1 L @ 2 L/min ≈30 s。算法能把“确认”压到 0.8 s，但压不掉腔体的低通。
3. **可用性已经是瓶颈**：M2i/M2j 要求湿腔不能启动、部分标定不能回收、确认 60 s。现场不会按实验室流程操作；不解决这个，数据永远来自“被照顾过的演示”。
4. **没有度量就没有优化**：两天内 15+ 个版本，说明当前循环是“改—看一份日志—再改”。先把 session/回放/20 次统计建起来，后面的每次改动才有可比性。
