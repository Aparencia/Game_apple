## 0. 结论速览

| 你观察到的现象 | 直接原因 | 类别 |
|---|---|---|
| ④ 清水被判"污水"、空气被判"清水" | **基线是在"电极露在空气里"时采的**：EC0 = 58.0 mV25，而干态电极实测只有 35~58 mV（均值 43.7）。此后**水位一淹到电极**，ΔEC 就是 +几百 mV → 必判 L2"污水"；**水位退回电极以下**，ΔEC 回到 0 附近 → 判 L0"清水"。判据测的是**"水位有没有淹到探头"**，不是水质 | 结构缺陷（致命） |
| ② 待机状态下"回收↔排空"阶段性跳跃 | 事件闩锁**只有 30 s 超时一个出口**；超时瞬间阀释放 → 12 V 线圈反冲让 3.3 V 轨/地弹跳 → ΔEC 被抬高 → 单点"变化率抢先"直接判 L2 → **自动开始新事件** → 200 ms 后回到 L0/CLEAR/回收。实测周期 30100 ms，与 `event_timeout_ms=30000` 完全吻合 | 设计缺陷 + 电气耦合 |
| ③ 只在开机时进待机，检测过就回不去 | 同上：每次回到 WAIT 都会被下一次瞬态立刻拉走；且 `auto_start_enable=true`、无"有水"门控 | 设计缺陷 |
| ④' 流速影响 | 判据实际是**液位/浸润**判据：流速决定腔体充不充满、探头露不露出、有没有气泡 | 结构 + 算法 |
| ⑤ 装置位置影响 | 探头电极**从瓶盖向上伸入腔体**，而腔体最低点就是出口 → 不流水就排空、电极露出 → 读数回落到 40 mV | 结构 |

一句话：**这套装置现在测的不是"水脏不脏"，而是"电极有没有被水淹到"。而"没淹到"有两种情况——根本没有水，或者有水但水位在电极以下——固件分不出这两种，一律判"清水"。而它的"干净参考零点"，正是在"没淹到"的时候取的。**

## 2. 从日志能反推出的事实

### 2.1 固件里存的"清水基线"= 电极露空时的读数

由 CSV 第 9 列 `g` 与第 8 列 `d_EC` 可反解出固件内部保存的基线：

```
g = EC/EC0 ,  d_EC = EC − EC0   ⇒   EC0 = d_EC / (g − 1)
```

186 帧反解结果：**EC0 = 58.02 mV25，标准差仅 0.127 mV**（说明这是一个上电时一次性写入的常量，不是实时量）。

而当前读数是 **43.7 mV25**（比基线还低 14.4 mV，`g=0.731`），186 帧全部落在 35.4~57.5 mV 之间 —— 电极一次都没被淹到，与"腔内无液体"一致。

（注：**电极露空**不等于"腔内无水"。下一次实验里"有水但水位低于电极"的情形，读数会落在同一个区间，固件无法区分——这正是 §3.5 的问题。）

结合你们自己的实验报告（`Docs/实验报告_拟TDS_电导率_传感器性能验证.docx` 表 4-2）：

| 状态 | 电压 | 备注 |
|---|---|---|
| 空气（探头**开路**，未插） | 1649.1 mV | 报告明确标注为"开路伪值" |
| 自来水 | 1490.6 mV | 报告结论：**基线必须取自自来水** |
| 皂液水 | 2356.3 mV | 正相 |

**结论：本机 58 mV 不是"开路伪值"，而是"探头插好、但电极露在空气里"的真实读数**（比开路低 28 倍）。两种"没淹到"的电气状态完全相反（一个 1.6 V、一个 0.04 V），固件只用一个 `EC0 ≥ 50 mV` 的门限来判"基线是否可信"（`sensor_pipeline.c:73 / :622`），**两个都放行**。

### 2.2 时间线还原（关键证据）

日志里只有 8 行 `#` 事件行（其中 2 行被串口截断），但它们把整条链路钉死了：

| t (ms) | 事件 | 我的还原 |
|---|---|---|
| 294139（推算） | — | 事件 N 开始（日志窗之前） |
| 324139 | `# EVENT end=TIMEOUT` / `# STATE CLEAR→WAIT` / `# ACTION DRAIN` / `# VALVE pos=DRAIN` | 满 30 s，超时 → WAIT + 排空，继电器**释放** |
| 324239（推算） | （该行被串口丢了） | 释放后 **2 个 tick**，模拟前端被瞬态打到 → `变化率抢先` 直接判 L2 → **auto_start 自动开事件 N+1** |
| 324439（推算） | — | 新事件 200 ms 块投票 4/4 = L0 → CLEAR → 请求回收 |
| 324639 | `# VALVE pos=RECOVER relay=1 count=11` | **正好 324139+500 ms = `APP_VALVE_MIN_DWELL_MS`**，驻留时间一到立刻吸合 |
| 354239 | `# EVENT end=TIMEOUT` / `# STATE CLEAR→WAIT` | 324239 + **30000 ms**，严丝合缝 |
| 354989 | CSV 首帧已回到 `RECOV` | 换向时刻被丢帧，按驻留推算 ≈354739 |

两处独立证据同时成立：
1. **周期 = 30000 ms**（324239→354239 = 30100 ms），只有 `event_timeout_ms` 这一个参数能解释；
2. **换向时刻 = 上一个沿 + 500 ms**，只有 `APP_VALVE_MIN_DWELL_MS=500` 能解释。

也就是说：**超时事件本身，成了下一次事件的触发器**。这是一个自激循环：

```
超时 → 阀释放 → 继电器/阀的电感反冲 → ADC 瞬态
   → |ΔEC| 够大且斜率 > +40 mV/s → 抢先判 L2（不等消抖）
   → 无事件 + auto_start_enable → 开事件（白送 30 s 回收许可）
   → 200 ms 后空气读数回落到 L0 → CLEAR → 阀吸合
   → 30 s 后超时 → 回到第一步
```

### 2.3 触发门限就长在执行器自己的干扰里（本次最硬的证据）

- 1 个 ADC 码 = 0.89 mV25（20 ℃ 时）；干态噪声峰峰 ≈ 20 码 ≈ 18 mV25。
- `ec_rate_th_mv_s = 40 mV/s` 在 400 ms 窗口里只需要 **16 mV25 / 18 个 ADC 码** 的变化。
- 全段最大的 4 个速率，**每一个都落在"继电器吸合"之后**（吸合时刻见 §2.2 的 500 ms 驻留推算，带 ≈ 者为推算值）：

  | t (ms) | 速率 | 参照换向 | 距吸合 |
  |---|---|---|---|
  | 324789 | −33.9 mV/s（85% 门限） | 324639 吸合（实测行） | +150 ms |
  | 324989 | −35.9 mV/s（90%） | 324639 吸合（实测行） | +350 ms |
  | 354789 | **−38.3 mV/s（96%）** | ≈354739 吸合 | +50 ms |
  | 354989 | −35.0 mV/s（88%） | ≈354739 吸合 | +250 ms |

  4/4 全为**负**向、4/4 都跟在**吸合**沿后面 → 这是一个**成对的特征**：

  > 继电器**吸合**（12 V 阀线圈浪涌）→ 3.3 V 轨/地弹跳 → ADC 读数**下陷** → ΔEC 速率 **≈ −35 mV/s**；
  > 继电器**释放**（线圈反冲）→ 同一个机构反向 → 速率 **≈ +35~+40 mV/s**，**正向**。
  >
  > 而 `decision.c:713` 的抢先判据只认**正向** `ec_rate_mv_s > +40`，消抖前的单点即可判 L2；
  > 于是**每次超时释放，就等于给自己发了一张 30 s 的回收许可**。

  负向那一半我们在 4 个点上全看到了；正向那一半正好落在被串口丢掉的 324189/324389/324589 三帧里（§2.4），**所以"释放沿触发 auto_start"是推断，但其镜像证据 4/4 成立**。

- 这也解释了为什么重开事件发生在超时后 **100 ms**：释放沿在 324139，ADC 在 324189 采样到抬高后的读数，400 ms 最小二乘斜率立刻变正，EMA 一次更新（α=0.35，raw≈+120 → EMA≈+41）就跨过 40 mV/s。

（可排除的替代解释见 §5 测试 A：若 `auto_start_enable=false` 后不再出现 RECOV，则本条成立。）

## 3. 五个现象逐条归因

### 3.1 现象 ④：电极被淹到判脏、露空判清 —— 基线取错了地方

`decision.c:319-341` 的三级分类是一个**纯相对**判据：

```c
if ((d_EC > e2_ec) || (d_ntu_pct > e2_ntu))  return L2;   // 脏
if ((d_EC < e1_ec) && (d_ntu_pct < e1_ntu))  return L0;   // 可回收
return L1;
```

它只会问"比基线**高**了多少"，从不问"基线本身是不是水"。于是：

| 基线取自 | 电极被水淹到（清水） | 电极露空（无水 / 水位低于电极） | 结果 |
|---|---|---|---|
| **露空态（本机，EC0=58 mV）** | ΔEC = +（清水读数−58）→ 必然 ≫ d2 → **L2 污水** ❌ | ΔEC ≈ 0 → **L0 清水** ❌ | 完全反了 |
| 清水（正确做法，EC0=清水读数） | ΔEC ≈ 0 → L0 清水 ✅ | ΔEC = −（清水读数−58）→ **L0 清水** ❌ | 一半对，另一半是隐患 |

（表中"清水读数"在本机尚未实测；旧面包板实验为 1490 mV，见 §5 测试 B。只要它比 d2=20 mV 大——几乎必然——结论就成立。）

**注意第二行**：把基线改到水里之后，**电极脱水**（水位降到电极以下，探头仍插着）会变成**巨大的负偏离**，而现分类器对负偏离**没有任何拦截**——它仍然判 L0/CLEAR/**RECOVER**。也就是说：（拔掉探头是"开路"，读数反而升到 ~1650 mV，会误报"脏"；真正危险的是"插着但没水"这种 58 mV 的负偏离。）

> 修好基线之后，会从"永远不回收"直接翻转成"没水/脏水也回收"。这是比现在更危险的状态，必须同时修。

### 3.2 现象 ②③：为什么"跳"、为什么"回不去"

`decision.c` 的事件闩锁结构：

```c
if (p_dec->event_active) {
    if (超时) { event_active = false; ... WAIT/DRAIN }      // 唯一出口
    else      { state = f(level); action = (CLEAR?RECOVER:DRAIN); }  // 事件内才可能回收
} else {
    if (auto_start_enable && !fault && baseline_valid && adopted==L2)
        { event_active = true; ... }                        // 唯一入口
    else { WAIT / DRAIN }                                   // 待机
}
```

问题叠加：

1. **入口太松**：`adopted==L2` 包括"变化率抢先"这条**单点、不等消抖**的路径（`decision.c:713-722`）。一次换向瞬态（几个采样）就能开事件。
2. **出口太晚**：一旦开事件，**只有 30 s 超时**能结束。中间哪怕水早没了、探头干着，也照样按 CLEAR 回收 30 s。
3. **没有"有水"判据**：整份代码没有流量计、没有液位、没有"探头是否在水中"的判断（`app_main.c:88` 注释也写了"无流量计"）。
4. **超时→释放→瞬态→再开**（§2.2），形成 30 s 自激。
5. 另有 `APP_VALVE_MAX_ON_MS=120000`（连续吸合 2 min 强制释放 + 10 s 冷却）——本应是一道兜底，但被 30 s 周期"喂"得永远到不了 120 s，等于失效。

**所以"待机"实际上不存在**：WAIT 只活 0.1~0.5 s 就被拉走。你看到的"回收→排空→回收"跳跃，周期就是 30 s。

### 3.3 现象 ④'：流速的影响（三个独立机制）

| 流速 | 腔体状态 | 探头看到什么 | 判据输出 | 危险性 |
|---|---|---|---|---|
| 0（静止/断流） | 排空，电极露出 | 40 mV 干态 | ΔEC≈0 → **L0 清水** | 高：脏水残留时也判清 |
| 低（< 腔体交换率） | 半满/液面在电极尖附近 | **时湿时干**，几十 mV 跳动 | L0↔L1↔L2 随机 | 最高：抖动即误动作 |
| 中 | 充满、无气泡 | 真实 EC | 唯一可信区间 | — |
| 高 | 气泡/飞溅/液膜 | 气泡绝缘 → EC **下降**；接触不稳 → 噪声大 | 偏向 **L0 清水** | 高：最容易把脏水放行 |

三个机理：

1. **湿/干切换**（主导）：电极朝上、腔体最低点就是出口，流速一低就露出来。你们报告 4.2 节也写了"入水 3.8 s 才进 ±1% 稳定带"——**探头从干到湿本身就是一个数秒级的大阶跃**。
2. **水力时间常数 ≫ 算法时间常数**：判据的时间尺度是 200 ms 块 / 500 ms 驻留 / 30 s 事件；而腔体的交换时间 `τ = V/Q`。按照片里的瓶/杯体积（百毫升级）与 0.1~0.5 L/min 估算：

   | 腔体容积 | 0.2 L/min 时的 τ | 结论 |
   |---|---|---|
   | 500 mL（整瓶） | **150 s** | 判据永远在描述 2 分钟前的水 |
   | 50 mL | 15 s | 仍比 200 ms 慢 75 倍 |
   | 5 mL | 1.5 s | 可用 |
   | 3 mL | 0.9 s | 目标区间 |

   **现在的判据是"快算法 + 慢水路"，等于用 0.2 s 的眼睛看 15~150 s 前的水。**
3. **气泡**：高流速下气泡贴在朝上的电极尖上，局部断路 → EC 偏低 → 判"更干净"。这正是你们报告表 5-1 里"泡沫/气泡会造成假判据"那一条，在实机上被放大了。

### 3.4 现象 ⑤：位置/结构的影响（对照照片）

照片里能确认的三件事，每一件都在把读数往"干态"推：

1. **探头从下方经绿色瓶盖插入，两根电极向上伸进腔体** → 电极是"最后被淹、最先露出"的位置；气泡也正好往上跑、贴在电极尖上。
2. **腔体最低点就是出口**（瓶盖/侧口在底部）→ 不流水就**必然排空**，探头必然回到 40 mV。于是"没水"才是常态，"有水"才是异常——而基线正好取在常态上。
3. **整机是重力自流**（顶上是 550 mL 瓶，下面接桶）→ 扬程随液位下降而衰减，流速从满瓶到半瓶能差一倍以上，§3.3 的湿/干边界会在一次洗手过程中**扫过**。装置放高放低、出水管口是否浸在接水桶里（虹吸/背压）都会改变腔体里的液位。

另外，**模拟线与继电器/阀的线在同一束里**（照片中红/黄/蓝线、黑线、继电器模块紧贴），TDS 模块 AOUT 是无屏蔽长线 → 这就是 §2.3 那 35~38 mV/s 瞬态的物理来源。目前固件里**没有任何换向后的屏蔽窗**。

### 3.5 两种"判清"对固件是同一件事（这才是要命的）

| 场景 | 电极状态 | 读数 | 固件判定 | 阀 | 实际后果 |
|---|---|---|---|---|---|
| **本次日志：腔内无液体** | 露空 | 43.7 mV | L0 CLEAR | **RECOV** | 回收空气（浪费，但不脏） |
| **另一次：有水，水位低于电极** | 露空 | 同一区间 | L0 CLEAR | **RECOV** | **回收水——可能是脏水** |
| 水淹到电极（清水） | 浸没 | 高 | L2（因基线是露空值） | DRAIN | 清水被排掉 |
| 水淹到电极（脏水） | 浸没 | 更高 | L2 | DRAIN | 正确 |

**前两行在固件眼里完全相同**：判据里没有任何"有没有水"的量，只有"EC 比基线高多少"。于是：

- **电极露空 → 判清 → 回收**：只要水位涨不到电极，水再脏也回收；
- **电极浸没 → 判脏 → 排空**：只要水位涨到电极，水再清也排掉。

两种错误方向同时存在，而且**方向由水位决定，与水质无关**。这也正好解释了你观察到的"清水被淹到就判污水、水位降下去就判清水"——它测的是水位越过电极那一瞬间。

**结论：`g` / `ΔEC` 只能回答"电极有没有浸没"，回答不了"有没有水"。** 这两个问题必须由两个信号分别回答：

| 要回答的问题 | 该用什么信号 | 现状 |
|---|---|---|
| 有没有水 / 在不在流 | 液位开关、流量计，或一对导通电极（几元） | **完全没有** |
| 水脏不脏 | TDS / 浊度 —— **前提是电极必须在最低水位以下**，保证"有水⇒浸没" | 电极在水位线以上，前提不成立 |

所以修复顺序必须是：**先改结构（让"有水"必然"浸没"），再改固件**。结构不改，固件怎么调都只是在"猜水位"。

### 3.6 浊度通道：在判据里，但这次一句话没说

**它确实参与了判别，而且有三处**（不是"没加入"）：

| 位置 | 作用 | 阈值 |
|---|---|---|
| `decision.c:332` | L0 的**必要条件**：`d_EC < e1` **且** `d_ntu_pct < e1_ntu` 才允许回收 | d1 = 8 % |
| `decision.c:325` | L2 的**充分条件**：任一路越上限即判脏 | d2 = 25 % |
| `decision.c:723` | 变化率抢先：`ntu_rate_pct_s > 50 %/s` 立即 L2（不等消抖） | 50 %/s |

方向在 `sensor_pipeline.c:680` 归一化（`ntu_clear_high=true`：清水电压高 → 变脏电压降低 → `Δ>0` 表示更脏）。

**但在这份日志里它一次都没触发**：

| 量 | 实测 | 阈值 | 余量 |
|---|---|---|---|
| `ntu_adc` | 1878~1932（均值 1904） | — | — |
| `ntu_node_mv` | 1513~1557（均值 1534.5，σ=6.6） | — | — |
| 还原 AO | 2270~2336 mV（均值 2302） | — | — |
| `d_ntu_pct` | **1.0~2.8 %（均值 1.53，σ=0.22）** | d1=8 % / d2=25 % | 差 5.2 / 22.2 个百分点 |

也就是说：186 帧里 L0 是"EC 通过 + NTU 也通过"的结果，但**决定权完全在 EC，浊度只是"没有反对"**。

**为什么"两路冗余"没能提高安全性**：因为两路共享同一个**共因故障**——

- 基线都在上电后同一段 1 s 窗口里、同一个 `pipeline_baseline_finish`（`sensor_pipeline.c:570`）采的，都是"腔内无液体"状态；
- TDS 在空气里 = 58 mV（等价于"极干净的水"）；
- 浊度在空气里 = AO ≈ 2337 mV，也落在"清水"端（模块清水输出高）。

**两路同时说"干净"**，所以冗余在这里完全失效。而且浊度比 TDS 更糟：

> 空气与清水在 TS-300B 上是**同一个方向**（都是高电压），所以"没水"对浊度而言看起来就是"非常干净的水"。TDS 至少还有一个绝对量可辨（58 mV vs 1490 mV），浊度没有——**只靠浊度永远分不出"空腔"和"清水"**。

由此得到一个重要的角色结论：**浊度只能"多排空"（否决回收），不能"少回收"**。它拦不住"空腔回收"，因为空腔在它眼里最干净。

**还有两个待标定的隐患**：

1. `d1=8 %`/`d2=25 %` 是拍的默认值（`app_main.c:194-195` 注释即"待标定"）。8 % 的 AO 变化 ≈ **187 mV**，25 % ≈ 584 mV。真实洗手水的浑浊度变化很可能只有几个百分点 → **浊度在这套门限下等于"不起作用"**。
2. 你们旧实验只测了 TDS（空气/自来水/皂液），**浊度的三态 AO 从来没有标过**，所以"浊度能不能分辨"目前是未知的，不能假设它有效。

**改法**（与 P0-2 同步做）：

| # | 改动 | 理由 |
|---|---|---|
| 1 | 浊度基线同样必须在水中采，并做"区间 + CV≤1 %"校验 | 与 TDS 同源问题 |
| 2 | 给浊度加**自己的"未浸没"判据**：AO 长时间贴近空载满量程（本机 ≈2.34 V）→ 判"无液体/未浸没" | 空气在浊度上就是满量程端，这个门限很自然 |
| 3 | 两路的"浸没"判据做**与/或组合**（先按"任一为否即视为未浸没"取安全侧） | 降低单路误判 |
| 4 | 用 §5 测试 B 补测浊度三点 AO（空载 / 清水 / 皂液），**按实测重设 d1/d2** | 8 %/25 % 现在没有任何依据 |

## 4. 修复方案

### P0 — 不改就会一直错（建议今天就做）

**P0-0 先把电极搬到"有水就浸没"的位置（结构，优先级高于一切固件改动）**

现在电极在水位线以上，所以"没水"和"有水但水位低"在固件里是**同一个输入**——任何算法都救不了。先改这里：

| 方案 | 做法 | 代价 / 效果 |
|---|---|---|
| A 最小改动 | 电极**缩短/下移**，尖端落在腔体底部 3~5 mm 的存水区 | 半小时，立刻见效 |
| B 推荐 | 出水口**下方**做一个小存水槽（φ15×10 mm ≈ 2 mL），电极插进去 | 存水槽常满；τ≈0.6 s @0.2 L/min |
| C 最好 | 换成**小容积流动腔**（下进上出，5~15 mL），电极横插或朝下 | 同时解决气泡、滞留与滞后 |

**验收**：任意水位（哪怕只剩几毫升）都应读到"浸没值"；抽干后 5 s 内回落到露空值。

**P0-1 禁止上电自动采基线**（`app_main.c:1776`）

```c
/* 步骤 9：上电自动采集基线（探头必须已浸在水样中） */
-    app_baseline_begin(timebase_ms(), NULL);
+    /* 不再上电自动采：干态采到的基线会让"任何水"都判脏。
+     * 改为显式命令 B / K2 长按，且必须通过 P0-2 的校验。 */
```

**P0-2 基线有效性必须是"区间 + 稳定性"双判据**（`sensor_pipeline.c:622`）

```c
-    valid = (mean_ec >= PIPELINE_MIN_VALID_EC0_MV);
+    /* 干态（本机实测 35~58 mV25）与开路伪值（~1650 mV）都不能当水样基线 */
+    bool in_band = (mean_ec >= p_pipe->cfg.ec0_min_mv) &&
+                   (mean_ec <= p_pipe->cfg.ec0_max_mv);
+    /* 1 s 内 CV > 1% 说明水没静下来（气泡/水流），重采 */
+    bool stable  = (sigma_ec <= (0.01f * mean_ec));
+    valid = in_band && stable;
```

`ec0_min_mv / ec0_max_mv` 做成配置项，**用 §5 的标定表来定**：`min` 取 max(3×干态读数, 湿态读数的 1/3)，`max` 取 2000 mV。附带好处：干态噪声 σ≈3.9 mV 在 43.7 mV 上就是 9%，**光靠 `stable` 这一条就能把干态基线刷掉**。

**P0-3 加"电极浸没"判据，并用它门控事件**（这是解决 ②③④ 的那一刀）

⚠️ 注意语义：这个判据回答的是**"电极有没有被水淹到"**，**不是"有没有水"**。二者只有在 P0-0 做完之后才等价。

基线一旦取自水样，`g = EC/EC0` 就是一个**与电极几何无关**的浸润判据（**前提：P0-2 已生效**，否则露空基线会把 g 抬到 0.73，反而误判"浸没"）：

```c
/* decision_update 里，健康检查之后 */
- bool wet = true;
+ /* g<0.3 且持续 1 s → 电极没被水淹到（水位低于电极/排空/开路/气泡） */
+ bool wet = (p_out->baseline_valid) && (p_out->g_ec >= DEC_EC_WET_RATIO); /* 0.3 */
```

然后：

| 位置 | 改法 |
|---|---|
| `decision.c:820` 自动开始 | 加 `&& wet` |
| `decision.c:788` 事件内 | 加 `if (!wet) → 结束事件、WAIT/DRAIN`（连续 1 s 判"未浸没"） |
| `decision.c:832` 待机 | `level` 在 `!wet` 时强制 L1（不许上报 L0） |
| `decision.c:325` 分类 | `if (d_EC < -e2_ec) return L1;` —— **大幅"变干净"同样是可疑事件**（电极脱水/气泡/水位下降），不是安全侧 |

**P0-4 修好 `max_on` 的兜底**：超时结束后加 10 s 锁定（`AUTO_START_LOCKOUT_MS`），锁定期间禁止 auto_start，否则 30 s 自激照旧。

### P1 — 让判据可用

| # | 位置 | 改动 |
|---|---|---|
| P1-1 | `app_main.c:196-198` | `ec_rate_th_mv_s` 40 → **120**（≥3× 实测瞬态 38），`ec_rate_min_jump_mv` 5 → 15 |
| P1-2 | `decision.c:713` | 抢先判 L2 必须**连续 2 个 tick 成立**，且**换向后 400 ms 内禁用**（`app_main` 提供一个 `valve_switch_age_ms`） |
| P1-3 | `decision.c:820` | auto_start 需要**连续 3 个块**都是 L2（约 600 ms），不接受单点 |
| P1-4 | `app_main.c:199` | `first_flush_ms` 2000 → **4000**，并让 auto_start 也走 FLUSH（你们报告实测 3.8 s 才稳定；现在 auto_start 是"直接进判别"，等于专挑瞬态下结论） |
| P1-5 | `sensor_pipeline.c` | 采样/滤波与流速匹配：`ema_alpha` 0.30→0.15、`baseline_n` 20→40，`block_ms` 200→400；或按 §3.3 的 τ 自适应 |
| P1-6 | `sensor_tds.c:136` | 补**低端**合理性检查：`mv25 < 30 mV` 持续 2 s → `SENSOR_ERR_RANGE`（现在只有 ≥4000 的高端 rail） |

### P2 — 硬件/结构（决定上限）

1. **换一个小容积流动腔**：5~15 mL，**下进上出**，保证流动时始终满、气泡能带走；目标 `V/Q < 1 s`。
2. **探头改卧式侧插、电极朝下**（或与流向垂直），彻底消除"朝上电极 + 气泡"的组合。
3. **阀尽量靠近探头**（现在探头在上、阀在下，检测到脏水时那一段已经流过去了）；按 `Q × t_decision` 估误排体积。
4. **模拟前端**：AOUT 加 RC（1 kΩ + 100 nF）+ 屏蔽线，与继电器/阀线分开走线，单点接地；继电器线圈侧加续流二极管（模块多数自带，确认一下）。
5. **加一个"有没有水"的硬信号**：一对不锈钢电极做导通检测（几元），或 YF-S201 流量计（十几元）。有了它，§3.2 那套"30 s 超时 + 超时自激"可以整段删掉。

## 5. 验证与标定（按顺序做，20 分钟）

### 测试 A：先排除"人为发 R"

烧一个只把 `auto_start_enable=false` 的固件，干态跑 5 min：
- 若不再出现 `RECOV` → 确认是 auto_start + 瞬态（§2.2）；
- 若仍出现 `RECOV`，看有没有 `# EVENT start=MANUAL` → 说明有人在发 R / RX 线被干扰，先查串口。

### 测试 B：三态标定表（必须用**本机**测，不要用旧面包板数据）

探头装回实机，用命令 `P` 看实时值，`B` 采基线：

| 状态 | 操作 | `tds_mv25`（均值±σ，60 s） | 浊度 AO（均值±σ） | 用途 |
|---|---|---|---|---|
| 干态 | 腔体排空、电极露空 | ______ mV ± ______ | ______ mV ± ______ | 定 `ec0_min_mv`（取 3×）与两路的"未浸没"判据 |
| 清水 | 自来水充满腔体、静置 | ______ mV ± ______ | ______ mV ± ______ | **基线 EC0 / NTU0** |
| 清水流动 | 正常洗手流量 | ______ mV ± ______ | ______ mV ± ______ | 看流速对读数的影响量 |
| 皂液 | 洗手液 1 mL/L | ______ mV ± ______ | ______ mV ± ______ | 定 EC 与 NTU 的 `d1/d2` |

判据自检：`Δ(皂液−清水) / σ(清水) ≥ 3` 才可用（你们旧报告 TDS 是 28，本机要重测）；**浊度这一列如果是 0 分不开，就说明它在实机上无效，应降级为纯辅助或直接停用**，不要因为它"在判据里"就假设它有贡献。

### 测试 C：状态机验收（五条，缺一不可）

1. 干态 60 s：必须**稳定 WAIT/DRAIN**，`state` 不许出现 CLEAR，阀不许吸合。
2. **有水但水位低于电极**（例如只放 20 mL，故意不淹到电极）：**不许回收**——这是当前最危险的组合，也是"清水被淹到才判脏"那次的对照。
3. 清水 60 s（淹到电极）：`CLEAR/RECOV` 稳定，无 30 s 周期跳变。
4. 清水 → 抽干：**5 s 内**回 WAIT/DRAIN 且阀释放（验证 P0-3）。
5. 皂液阶跃：**≤1.5 s** 内切 DRAIN（验证 P1-2/P1-3 没把响应拖太慢）。

## 6. 一句话给答辩/报告用

> 本次"无液体"实测暴露的不是传感器精度问题，而是**参考零点与状态机语义**的问题：装置把"电极露在空气里"当成了"清水本底"（EC0=58 mV，而自来水应为数百至 1500 mV 量级），于是判据退化为"**电极有没有被水淹到**"——淹到必判脏、没淹到必判清。而"没淹到"既可能是没水，也可能是**有水但水位在电极以下**，固件分不出这两种：前一种只是回收空气（浪费），后一种会把脏水直接送进回收箱。浊度虽然也在判据里（L0 的必要条件 + L2 的充分条件 + 速率抢先），但它与 TDS 共享同一个"干态"基线，且空腔在浊度上恰好等于"最清的水"（AO≈2337 mV），**所以两路冗余在同一时刻给出同一个错误答案，兜不住**；本次 186 帧里 `d_ntu_pct` 仅 1.0~2.8 %，离 8 %/25 % 的门限还远，等于没参与。同时事件闩锁只有 30 s 超时一个出口，超时瞬间换向引起的瞬态又能通过"变化率抢先"重新开事件（实测周期 30100 ms、换向延迟 500 ms 与固件常量逐位吻合），造成回收/排空周期性跳变且永不回到待机。修复方向：①先把电极搬到"有水必浸没"的位置；②两路基线都必须在水中采并做区间+稳定性校验；③用"电极浸没"判据门控事件、并单独补一路"有没有水"的信号；④换向后加屏蔽窗、提高变化率门限；⑤按实测重标浊度门限，分不开就停用。
